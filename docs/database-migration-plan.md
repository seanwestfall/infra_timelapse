# Database migration plan

This is the first concrete PostgreSQL/PostGIS implementation for issues #3 and #4. Structural migrations remain separate from the versioned inventory seed and are applied in filename order inside individual transactions.

## Structural order

| Order | File | Responsibility |
|---:|---|---|
| 1 | `0001_extensions_and_schemas.sql` | Enable PostGIS and create `catalog`, `evidence`, and `observation`. |
| 2 | `0002_reference_types_and_sources.sql` | Create enums, countries, provenance sources, and seed releases. |
| 3 | `0003_catalog_entities_and_nodes.sql` | Create stable entities, nodes, aliases, jurisdictions, role-based node geometries, and node links. |
| 4 | `0004_catalog_corridors_and_projects.sql` | Create corridor routes and memberships plus projects, organizations, and project parties. |
| 5 | `0005_evidence_claims_and_status.sql` | Create relationship assertions, lifecycle history, and their source links. |
| 6 | `0006_observation_metadata.sql` | Create monitoring runs and external imagery metadata without image binary columns. |
| 7 | `0007_constraints_and_indexes.sql` | Add promotion gates, current-row uniqueness, foreign-key lookup indexes, and GiST indexes. |
| 8 | `0008_verification_and_identity_guards.sql` | Make entity identity immutable, close reassignment/source verification bypasses, and block corridor/project verification until dedicated gates exist. |

Canonical vectors use EPSG:4326. Node geometry roles constrain centroids to `Point`, facility boundaries and satellite AOIs to `MultiPolygon`, and route centerlines to `MultiLineString`. Corridors use `MultiLineString`; imagery footprints use `MultiPolygon`. Geometry checks reject empty, non-2D, or wrong-SRID values. Global proximity queries use a partial GiST expression index over centroid `geography` casts.

## Seed order

`db/seeds/infra-inventory-v0.1.0/seed.sql` runs all seed components in one transaction:

1. Countries, provenance sources, and the seed release.
2. Stable UUIDv5 entities and node/corridor/project subtype rows.
3. Aliases, jurisdictions, source centroids, and facility links.
4. Corridor geometries and memberships, project mappings, organizations, and parties.
5. Relationship assertions, lifecycle history, and provenance links.
6. Count, identity, normalization, geometry, topology, and effective-period assertions.

The committed SQL is generated by `scripts/build_seed.py`. `--check` rejects drift between the source inventory, normalization rules, and generated files. Upserts refresh seed-owned descriptive fields while preserving curated workflow state; records missing from a future seed are not deleted implicitly.

## Validation order

`make db-test` executes the publication gate in this order:

1. Rebuild the in-memory seed model and run deterministic normalization tests.
2. Verify generated SQL is current.
3. Apply checksum-tracked migrations to an empty or existing database.
4. Apply the seed, mutate curated workflow state, and replay it to prove idempotency without resetting that state.
5. Verify PostgreSQL/PostGIS health and the expected GiST indexes.
6. Re-run seed invariants, immutable-identity checks, and promotion/dependency constraints.
7. Run AOI intersection, corridor/chokepoint intersection, and global-distance smoke queries.

The initial scope deliberately excludes the full CPORTS import, imagery downloads, raster analytics, and an API. Those additions should use new migrations and seed releases rather than changing an applied migration or the v0.1 seed identity.
